# 多模態：影像、聲音、影片

Jev 只讀文字與 JSON。官方文件說影像、聲音、影片「尚未支援」。所以含 Jev 的多模態流程只有一種形狀：

```text
感知模型（視覺 LLM、OCR、語音辨識、偵測器）→ 文字或結構化欄位 → Jev 判斷文字
```

感知那一步產出文字；Jev 決定那些文字對你的政策意味著什麼。前面章節裡 Jev 出現的每個位置都仍然成立，只是往右移一步。

## Jev 在媒體周邊仍然值得的地方

- **在昂貴的視覺呼叫之前。** 關於一個檔案的多數決定，可以從它周圍的東西做出：檔名、資料夾、寄件者、說明文字、EXIF、隨附的訊息。對這些後設資料問「這個附件像收據嗎」花 0.00001 美元；視覺呼叫貴一百倍、慢一兩秒。先設關卡。
- **對感知模型的文字。** 視覺模型寫「發票總額 12,480、截止日 25 日」，或寫一段生成片段的缺陷報告。Jev 把這些發現歸進你的固定分類、檢查報告是否真的得出通過或不通過、標出文字與判決之間的矛盾。這正是本工具包背後那個生產 repo 的分工：視覺模型看畫面，Jev 結構化審查。
- **在候選中挑選。** OCR 對一行給三種讀法；語音辨識給 n-best 清單；描述器給五個標題。Jev 挑跟脈絡一致的那個。挑選，不是生成。
- **不看媒體就驗證關於媒體的宣稱。** 「逐字稿支持這段摘要嗎？」「替代文字描述的是圖說說的東西嗎？」文字對文字。
- **把逐字稿變成決定。** 會議錄音 → 逐字稿 → 逐段 Jev 問題：這是行動項嗎、誰負責、這是決定還是未決問題。聲音模型聽，Jev 分類。

## 行不通的

- 送 base64 或網址然後期待。API 只接受字串、物件或文字陣列的 state。圖片網址對它只是一串字。
- 透過描述問 Jev 像素的事。「髮絲邊緣乾淨嗎」無法從檔名回答。判斷是視覺的，就由視覺模型做；Jev 只能判那個模型寫下的東西。
- 從影像抽出的數字。OCR 的數字是文字，但比較、加總、日期運算仍然屬於程式碼。

## 具體配方

1. 感知：用視覺或聲音模型，prompt 要求**發現而非判決**：它看到什麼，平鋪直敘地列出。
2. 結構化：對這些發現發一次 Jev 請求，問你的固定問題：每個發現的分類、嚴重度、是否阻擋、是否與所述判決矛盾。
3. 政策：程式碼從型別化答案決定通過、重試或升級，並把發現、答案、決定一起記錄。

第 2 步便宜到每個檔案都能跑，穩定到能用過去的發現做黃金測試集。第 1 步仍然昂貴，仍然留給看得見的模型。
