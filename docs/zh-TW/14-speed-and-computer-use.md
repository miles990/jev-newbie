# 速度，以及 computer use

## 速度：我們量到的

`examples/js/latency.mjs`，從台灣，2026-09-19，`jev-1.13.0`，直連 API：

```text
15 sequential calls, 1 question:      min 218 · p50 259 · p90 586 · max 788 ms
15 sequential calls, 13 questions:    min 213 · p50 266 · p90 338 · max 350 ms
20 parallel calls, 13 questions:      min 310 · p50 668 · p90 723 · max 739 ms   wall clock for all 20: 744 ms
same request twice (no client cache): 201 ms then 238 ms
```

實務上的意思：

- **一次呼叫約四分之一秒**，端對端含 TLS。官方數字 70 到 500 毫秒；多出來的主要是距離。預算抓典型 300 毫秒、最差 800 毫秒。
- **問題數不增加延遲。** 十三題與一題花的時間一樣（p50 266 對 259 毫秒）。這是 Jev 最重要的效能事實：永遠不要為了「快」把問題拆到多次呼叫，要反過來。
- **平行呼叫也幾乎免費。** 二十次同時發出，744 毫秒內全部完成；單次延遲升到約 670 毫秒因為共用連線，但單一程序不調校就有每秒 27 次的吞吐。天花板是速率上限（撰寫時每分鐘 1,200 次、每秒 250k token），不是客戶端。
- **伺服器不快取重複請求。** 同一請求兩次花 201 與 238 毫秒。在你的程式碼裡以請求雜湊快取；`jev` CLI 與這裡每支腳本都有，命中是 0 毫秒。
- **跟 LLM 呼叫比**（兩到十秒、每次幾美分），Jev 快十到四十倍、便宜一百倍。這就是它能塞進迴圈、站在每個昂貴步驟前面的原因，LLM 永遠做不到。

速度最重要的場合：

| 場合 | Jev 合不合 | 證據 |
| --- | --- | --- |
| UI 裡逐訊息路由 | 遠低於人能感覺的延遲 | p50 259 毫秒 |
| agent 工具呼叫關卡 | 每次呼叫、每次回傳 | pi-jev、jev-guard 每步都跑 |
| 批次貼標 | 單一程序幾分鐘處理幾千筆 | 實測每秒 27 次；多程序更多 |
| 即時控制迴圈 | 2 到 10 Hz 的顧問，不是內迴圈 | jev-drone 2.5 Hz、社群 FPS 約 9 Hz、typesafe-mario 每 8 幀 |
| 收斂迴圈 | 每輪重打整批 | 12 項 × 3 輪幾秒 |

不夠快的場合：每個決策需要幾千次評估的（完整 MCTS 內迴圈），或 100 毫秒以下的硬即時期限。做狀態指紋與快取、或預算成表，就又合了。

## Computer use：Jev 看不到螢幕，仍然能操作它

社群裡每個「Jev 驅動瀏覽器或桌面」的專案都是同一種做法，也跟多模態那章同一個形狀：

```text
螢幕 → 文字表示 → 候選 → Jev 選動作 → 程式碼執行 → 重複
```

文字表示是關鍵：瀏覽器的 DOM 或無障礙樹、桌面的無障礙 API、帶座標的 OCR 文字區塊。每個可互動元素變成一個候選，有 id、角色、可見文字。Jev 對這些候選回答一個 `choice`（「哪個元素推進目標？」）加幾個 `noul`（「目標完成了嗎」「這是登入或付款步驟嗎」「上一步失敗了嗎」）。程式碼去點。需要打字時才叫 LLM 寫；那是唯一的生成步驟。

正是這樣做的專案：

- **jev-ultrafast**（browser-use 團隊）：Jev 決定每一步的動作與元素，需要文字才叫小模型；Google Flights 搜航班整趟約 7 秒。
- **fastbrowse、Jev Browser、public-browser**：同樣模式，最後一個從 Claude Code 驅動真實 Chrome profile，回報 token 少約三成、成本低約四分之一。
- **jev-desktop**：讀作業系統的無障礙樹，替本機執行器選控制項與動作。
- **trycua/cua jev-use**：computer-use 驅動器，動作選擇是對帶座標與信心的 OCR／文字區塊做有界的 Jev `choice`。

為什麼可行：一個畫面最多幾十個可操作元素，「哪一個」是封閉集合；目標是文字；每步 300 毫秒讓二十步的任務幾秒完成。為什麼比 LLM 直接駕駛安全：動作空間由程式碼列舉，Jev 不會發明一個點擊；每個有風險的步驟（「這是付款嗎」）只是同一請求裡多一題。

做不到的：只有 canvas 沒有文字的介面、以像素渲染的遊戲、正確元素不在候選清單裡的情況。這些要先由視覺模型產生候選，Jev 再從中挑。而且 computer-use agent 仍需要前面章節的關卡：每次點擊前的破壞性檢查、先 shadow 模式、付款與憑證交給人。
